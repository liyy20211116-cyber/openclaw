# OpenClaw 国内多模态模型接入设计

## 1. 当前仓库现状

我先基于你当前机器上的 `d:\FY003` 和运行配置做了梳理，结论如下：

- 这个根目录本质上是一个 `OpenClaw` 使用层工程，不是上游源码仓。
- 根目录 `package.json` 只依赖了 `openclaw@2026.3.2`。
- 真正的程序代码在 `node_modules/openclaw`，不是 `d:\FY003\OpenClaw`。
- 你当前的运行配置不在仓库里，而是在 `C:\Users\Lenovo\.openclaw\openclaw.json`。
- 你现在的默认主模型是 `openai-codex/gpt-5.3-codex`，fallback 是 `ollama/qwen2.5:7b`。
- 已启用的关键插件是 `feishu`、`llm-task`、`qwen-portal-auth`。
- 根目录 `scripts/` 目前主要是新闻/视频生产脚本，不是模型 provider 接入层。

这意味着一件很重要的事：

- 如果只是“加模型”，应该改 `~/.openclaw/openclaw.json`、插件开关、工具白名单和外部脚本。
- 如果是“深改 OpenClaw 的 provider/runtime 行为”，应该单独拉 OpenClaw 源码仓，不要长期改 `node_modules/openclaw`。

## 2. 当前最大短板

你现在不是模型不够多，而是缺少统一分层：

1. 主模型路由层
2. 图像/视频生成工具层
3. 语音输入输出层
4. 密钥与配额治理层

另外我在当前环境里看到两类高风险问题：

- `.env` 和 `C:\Users\Lenovo\.openclaw\openclaw.json` 里存在明文敏感信息。
- 当前国产模型并没有进入统一路由，只是零散地出现在插件和脚本白名单里。

建议：

- 立即把现有明文 key 迁移为 `${ENV_VAR}` 或 SecretRef。
- 已暴露过的 key 建议轮换。

## 3. 设计原则

你的目标不是“把所有模型都设成默认”，而是让 OpenClaw 在不同任务上自动选对能力层。

我建议把体系拆成四层：

### A. 主推理层

负责：

- 聊天
- 编程
- Agent 推理
- 工具调用规划
- 多轮对话

这层适合接入：

- DeepSeek
- 通义千问 Qwen
- 智谱 GLM / Z.AI
- Moonshot / Kimi
- MiniMax
- 本地 Ollama

### B. 媒体理解层

负责：

- 看图
- 音频转写
- 视频理解

这层不要和主模型层混用。OpenClaw 当前内置媒体理解支持是有边界的，国内 provider 不能全部直接塞进去。

### C. 生成工具层

负责：

- 文生图
- 图生图
- 文生视频
- 文本转语音
- 语音识别

这层最适合用“外部脚本 + 工具白名单”或“本地插件”。

### D. 密钥与策略层

负责：

- 免费优先
- 失败回退
- 国内优先
- 配额保护
- 不同任务选择不同 provider

## 4. 国内模型怎么映射到 OpenClaw

这里要避免把“消费端产品名”和“开发者 API 平台名”混在一起。

### 4.1 DeepSeek

适合角色：

- 文本推理
- 代码
- 低成本补位

接入方式：

- 作为 `models.providers.deepseek`
- 走 OpenAI 兼容接口

设计判断：

- 截至 2026-03-07，我查到的官方开发文档主要还是文本/推理接口，没看到稳定的官方图像/视频/TTS/STT 产品线入口。
- 所以 DeepSeek 应放在“主推理层”，不放在“多模态生成层”。

### 4.2 通义千问 / Qwen

适合角色：

- 免费文本/代码入口
- 视觉理解
- 后续扩展图片/视频/语音

接入方式分两种：

1. 免费优先：直接用 OpenClaw 已内置的 `qwen-portal-auth`
2. 稳定 API：接阿里云百炼 DashScope

设计判断：

- `qwen-portal-auth` 已经在你环境里启用了，这是最快的免费入口。
- 如果你要图像、视频、语音能力，应该补一层 DashScope 工具脚本，而不是只靠 `qwen-portal/coder-model`。

### 4.3 智谱清言 / GLM / Z.AI

适合角色：

- 国产主力推理模型
- 免费 flash 模型
- 图像/视频/语音扩展

接入方式：

- 文本主模型直接走 OpenClaw 内置 `zai/*`
- 图像/视频/语音走智谱官方 API 包装成工具

设计判断：

- “智谱清言”是产品名，OpenClaw 真正该接的是开发平台 `Z.AI` / `BigModel`。
- 这类能力非常适合做你国内模型池里的核心 fallback。

### 4.4 Moonshot / Kimi

适合角色：

- 长上下文问答
- 中文写作
- 国内代码/推理补位

接入方式：

- `models.providers.moonshot`
- OpenAI 兼容接口

设计判断：

- 这层适合直接进主模型池。
- 适合做国内主力之一，不适合拿来代替图片/视频/语音工具层。

### 4.5 MiniMax

适合角色：

- 文本推理
- Coding Plan OAuth
- 语音/图像类能力的后续扩展

接入方式：

1. 免费/低门槛登录：`minimax-portal-auth`
2. API Key：`models.providers.minimax`

设计判断：

- OpenClaw 已经内置了 `minimax-portal-auth`，你现在只是还没启用。
- MiniMax 可以进入主模型池。
- 但如果你想把 MiniMax 的语音/图像能力真正接入 OpenClaw，对你当前这套安装方式来说，更稳的是工具化，不是硬改内置 TTS。

### 4.6 即梦 AI / 火山引擎

适合角色：

- 图像生成
- 视频生成
- 语音识别
- 语音合成

接入方式：

- 不建议把“即梦 AI”当主聊天 provider
- 建议作为“图像/视频/语音工具层”
- 通过火山引擎视觉/语音 API 包装成脚本或本地插件

设计判断：

- 即梦更像能力来源，不是主推理 brain。
- 你真正应该接的是火山引擎或其开发者 API，而不是产品网页端。

## 5. OpenClaw 现有能力边界

这个边界非常关键，决定你怎么做不容易烂尾。

### 5.1 文本主模型层

OpenClaw 现在非常适合：

- 内置 provider
- OAuth provider
- OpenAI 兼容 provider
- Anthropic 兼容 provider

所以以下很容易接入：

- Qwen OAuth
- GLM / Z.AI
- Kimi / Moonshot
- DeepSeek
- MiniMax

### 5.2 媒体理解层

OpenClaw 当前内置的 `tools.media` 更偏向：

- OpenAI
- Google
- Groq
- Deepgram
- CLI fallback

这意味着：

- 国内文本模型很好接
- 国内音频/视频/图像理解并不是都能直接用 `tools.media` 无缝替换

结论：

- 国内媒体理解建议优先“脚本工具化”
- 不建议一开始就硬改 OpenClaw 内部媒体 provider

### 5.3 TTS 层

你当前版本里，`messages.tts` 内置只明显支持：

- `edge`
- `openai`
- `elevenlabs`

所以：

- 想要免费 TTS，先用 Edge TTS
- 想接国内 TTS，应该做你自己的工具/插件层

## 6. 推荐架构

我建议你按下面这个结构做，而不是把所有模型都直接堆到默认模型上。

```text
Feishu / OpenClaw Session
        |
        v
主 Agent 路由层
  - Primary: OpenAI Codex 或 Qwen OAuth
  - Fallback: GLM / Kimi / DeepSeek / MiniMax / Ollama
        |
        +--> 文本任务 -> 主模型池
        |
        +--> 看图/听音/看视频 -> 媒体工具层
        |
        +--> 生图/生视频 -> 生成工具层
        |
        +--> TTS / ASR -> 语音工具层
```

### 我的推荐主模型池

按优先级建议这样排：

1. `openai-codex/gpt-5.3-codex`
2. `qwen-portal/coder-model`
3. `zai/glm-5`
4. `moonshot/kimi-k2.5`
5. `deepseek/deepseek-chat`
6. `minimax/MiniMax-M2.5-highspeed`
7. `ollama/qwen2.5:7b`

这个结构的好处：

- 仍保留你当前最强 coding 主力
- 增加国内免费/低价 fallback
- 任何一家炸掉时不至于整体瘫痪

## 7. 实施路线

### 第一阶段：零风险接入文本层

只做配置，不改 OpenClaw 内核：

- 启用 `qwen-portal-auth`
- 启用 `minimax-portal-auth`
- 加入 `zai`
- 加入 `moonshot`
- 加入 `deepseek`
- 保留 `ollama/qwen2.5:7b`

目标：

- 让你的主对话和 agent 推理先具备“国内多 provider fallback”

### 第二阶段：工具化接入图片/视频/语音

新增你自己的脚本工具：

- `scripts/cn_image_gen.py`
- `scripts/cn_video_gen.py`
- `scripts/cn_tts.py`
- `scripts/cn_asr.py`

把它们加入 `tools.allow`。

这些脚本内部再按能力选 provider：

- 图像生成：DashScope / 智谱 / 即梦 / MiniMax
- 视频生成：DashScope / 智谱 / 即梦
- TTS：MiniMax / 火山 / 阿里语音
- ASR：火山 / 阿里 / 智谱

### 第三阶段：做本地统一路由器

如果你后面希望“所有国内能力都统一调度”，再做一个本地服务：

- 名字建议：`cn-model-router`

职责：

- 统一密钥读取
- 配额控制
- provider fallback
- 将不同平台输出统一成一个 JSON 协议

这样 OpenClaw 只需要调用一个本地服务，不需要理解每一家平台的差异。

## 8. 我不建议的做法

### 不建议 1：直接修改 `node_modules/openclaw`

原因：

- 升级就丢
- 很难维护
- 容易和上游版本漂移

### 不建议 2：把图片/视频/语音模型全塞进默认主模型

原因：

- OpenClaw 的主模型路由和生成工具不是一个抽象层
- 会导致调用策略混乱

### 不建议 3：只看“免费”不看接口稳定性

原因：

- 免费网页端不等于免费开发者 API
- OAuth 免费模型适合入口，不适合承载全部生产流量

## 9. 最终建议

你的目标应该是：

- 文本主脑：国内外混合
- 图片/视频/语音：国内平台工具化
- 免费优先：Qwen OAuth、GLM 免费模型、Edge TTS、本地 Ollama
- 稳定优先：DeepSeek / Kimi / MiniMax / Z.AI

一句话总结：

不是“把所有国内模型都接成默认模型”，而是“把国产模型分层接成一个可路由、可回退、可控成本的能力栈”。
